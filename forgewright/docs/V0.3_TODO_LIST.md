## How to read this list

Items are grouped into **5 horizons**, ordered by "what unblocks what". Each item
has a one-line summary, a Why (the leverage), a What (the concrete shape), a
How (the smallest viable implementation), an Effort (S/M/L), and Dependencies.

Effort key:
- **S** = &lt; 1 day, single PR, no architectural change
- **M** = 1–3 days, touches 1–2 subsystems, needs a new test file
- **L** = 1+ weeks, touches 3+ subsystems, needs an RFC

Horizons are **not** calendar dates — they're a dependency chain. A horizon
can be worked in parallel with the next one if the items are independent.

## Horizon 1 — Two-agent shared workspace (smallest credible v0.3 milestone)

> Two items. They unblock the bigger H2 crew flows and H2 realtime collab
> by establishing the **shared event log / workspace** primitive that both
> depend on.

### H1.1 — Append-only log fan-out (no WS yet, just `?since=` polling)
- **What:** `src/forgewright/security/audit.py:238-245`. Add a streaming
  matcher to `AuditLog.query()` so it can iterate a 10k-line JSONL without
  loading all of it into RAM. Pair with a `?since=<offset>` query param on
  `GET /api/sessions/{id}/events` that streams new events as they arrive.
- **Why:** Crew flows will generate 10× the audit events per session;
  realtime collab will need multi-reader access to the same log. This is
  the shared foundation. **Yjs is overkill for v0.3 — append-only log
  fan-out is the proven pattern (OpenHands V1, Linear-class apps).**
- **Effort:** M (1 day: 80 LOC refactor + new tests).
- **Deps:** H0.7 (REPO trust) is nice-to-have for security scoping; not
  required.

### H1.2 — Workspace sharing: shared `Workspace` object on the ToolCollection
- **What:** `src/forgewright/flow/planning.py:222-242` + `src/forgewright/agent/manus.py:42-49`.
  A workspace-aware tool collection that watches a shared directory
  (inotify on Linux, FSEvents on macOS, polling on Windows) and lets the
  next sub-agent discover the previous agent's edits without an explicit
  `StrReplaceEditor` round-trip.
- **What shape:** a `Workspace` ABC (Local, Docker-volume, Remote-SSH) per
  the OpenHands V1 `BaseWorkspace` pattern. `FileEditor` writes flush to
  the workspace, not a per-agent tmp dir.
- **Why:** Required for any non-trivial multi-agent pattern. Today the
  multi-agent flow requires the LLM to *remember* to look for files
  that don't exist yet.
- **Effort:** M (1–2 days, ~120 LOC).
- **Deps:** H0.8c (`max_output_chars` shared), H1.1 (event log fan-out for
  the workspace-changed event).

## Horizon 2 — The five v0.3 roadmap deliverables (the "real" v0.3 work)

> Five items. Most are L; each is its own PR. They were the v0.3 candidates
> in `ROADMAP.md` going into v0.2.0.

### H2.1 — `Crew([A, B, C])` first-class multi-agent primitive
- **What:** A new `src/forgewright/flow/crew.py` exposing
  `Crew([Manus(...), BrowserAgent(...), DataAnalysis(...)])` with
  explicit handoff. Build on `PlanningFlow._execute`
  (`flow/planning.py:288-294`) but allow parallel steps, fan-out, and
  a shared blackboard. Persist agent hand-offs as a typed audit event.
- **What shape (per external research):**
  - First-class `Crew([A, B, C])` with explicit handoff (matches ROADMAP)
  - **Add:** `ConversationState` event-sourced view over the existing
    JSONL audit log (the AutoGen v0.4 / OpenHands V1 consensus)
  - **Add:** sub-agent-as-a-tool (matches OpenHands V1)
  - Defer: cross-process agent transport (v0.4)
- **Why:** The single biggest v0.3 unlock. Unblocks every other
  multi-agent feature.
- **Effort:** **L** (1–2 weeks, 300–500 LOC + tests).
- **Deps:** H0.7 (REPO trust), H0.8d (memory settings), H1.1 (event log),
  H1.2 (shared workspace).
- **Test cases (mandatory):**
  - **Loop detection** (`deque(maxlen=3)` of `(tool_name, args_hash)`,
    raise `AgentLoopDetectedError` and emit typed final state) — see
    C3 in external research.
  - Adversarial: a tool that returns "more results may be available"
    50× → loop detection fires.
  - Two agents writing the same file → workspace-level write
    serialisation (not FS).

### H2.2 — Event-sourced `ConversationState` shim
- **What:** A thin shim over the existing JSONL audit log that exposes
  `ConversationState` as a queryable, re-playable view. The shim is
  the foundation for H2.1, H2.3, and H2.5.
- **What shape:** `ConversationState.from_log(path, session_id) -> state`,
  `state.events: list[TypedEvent]`, `state.replay(from_offset) -> AsyncIterator`.
  Built on top of the existing `AuditEvent` schema. No new persistence
  layer.
- **Why:** OpenHands V1's full deterministic replay is a v0.4 feature.
  The shim is enough to support cost caps, crew flows, and realtime
  collab. Per the external brief: *"The shim is enough: write events
  to the JSONL audit log, expose a `ConversationState` view."*
- **Effort:** M (1–2 days, ~200 LOC).
- **Deps:** H1.1 (streaming query).
- **Pairs with:** H2.1, H2.3, H2.5.

### H2.3 — Per-session cost caps (`--max-cost=$X` + `--max-iterations=N`)
- **What:** A pre-call + post-call hook in the `LLM` protocol layer.
  `Settings.cost.max_usd_per_session` and `Settings.cost.max_iterations_per_session`.
  Exceeding either aborts the loop and persists `"final_state": "cost_limit_reached"`
  to the session JSON. Pair with a `forgewright cost refresh` subcommand
  to update the pricing table from a public feed.
- **Why:** The LiteLLM `max_budget_per_session` pattern is the proven
  approach. **This is URGENT** — OpenAI removed its hard monthly cap
  in early 2026, replaced with email-notification soft limit. The
  $72k overnight retry-loop incident is a real failure mode. User-side
  enforcement is the only safe answer.
- **Critical shape:**
  - Pre-call hook checks accumulated cost **before** the LLM call
  - Post-call hook increments after the LLM responds
  - `max_cost` AND `max_iterations` (single cap is not enough — different
    attack profiles)
  - Persist "cost limit reached" as a typed final state in JSONL
    audit log, not as an exception
- **Effort:** M (1 day, ~100 LOC; 80 LOC of tests).
- **Deps:** H0.8b (pricing table from settings), H2.2 (ConversationState
  for the typed final state).
- **Test cases (mandatory):**
  - `test_cost_cap_fires_pre_call` (C2 from external research)
  - `test_iteration_cap_fires_independently`
  - `test_free_tier_model_does_not_increment`
  - `test_error_response_does_not_increment`
  - `test_cost_limit_reached_typed_state` (not `RuntimeError`)

### H2.4 — Provider failover with tool-call schema adapter
- **What:** Wrap `litellm.acompletion()` in a retry + fallback chain
  sourced from `Settings.llm.fallbacks: list[LLMConfig]`. Catch
  `litellm.exceptions.APIConnectionError`, `Timeout`, `ServiceUnavailableError`,
  `RateLimitError`, and HTTP 5xx; fall over to the next entry. Circuit
  breaker: 5 consecutive failures, 60-second cooldown.
- **What shape (per external research):**
  - Retries with exponential backoff + jitter (transient: 429, 500, 502,
    503, 504, timeout)
  - Prioritised fallbacks (`primary → cheaper-same-provider →
    cross-provider → self-hosted`)
  - Circuit breaker (5 fails trip, 60s cooldown)
  - **Tool-call schema adapter** — the single most critical piece.
    Anthropic `tool_use`, OpenAI `function_call`, Gemini `function_calling`
    differ. Normalize to one versioned schema, pass through on failover.
    Without it, falling over from Anthropic to OpenAI **silently breaks
    tool calls** — worse than not failing over.
- **Why:** Production must-have. Anthropic had 114 incidents in a 90-day
  window in early 2026. Single-provider outage = total user-visible
  downtime. The current `litellm_backend.py` has zero retry/failover logic.
- **Effort:** **L** (1 week: ~150 LOC for the failover chain, ~200 LOC
  for the schema adapter, ~200 LOC of tests).
- **Deps:** H0.8a (context tokens from `litellm.get_max_tokens`),
  H0.8f (per-call `drop_params`).
- **Test cases (mandatory):**
  - `test_failover_emits_user_visible_status_within_2s` (C1)
  - `test_anthropic_to_openai_tool_call_round_trip` (C4)
  - `test_all_fallbacks_exhausted_returns_typed_failure`
  - `test_circuit_breaker_trips_after_5_failures`
  - `test_openrouter_served_model_audit_divergence` (C5)

### H2.5 — Realtime webchat collab (multi-user WebSocket fan-out)
- **What:** Add a WebSocket endpoint at `/api/sessions/{id}/ws` that
  fans out new events to all subscribers. Extend the PWA service
  worker with a "WS upgrade bypass" rule (so the SW doesn't intercept
  WebSocket handshakes).
- **What shape (per external research):**
  - **Do NOT introduce Yjs yet** — append-only log fan-out
    (single-writer, multi-reader) is the proven pattern
  - WebSocket fan-out over the existing event log
  - Presence (cursor / who's-typing) is a tiny Yjs awareness doc
    *separately*. Don't mix it with the JSONL log.
  - Defer: real-time collab on the **agent's tool output** (v0.4)
- **Why:** The PWA can only be used by one client at a time per session
  today. Useful for desktop+phone sync (the "federated sessions"
  roadmap item's MVP).
- **Effort:** **L** (1 week: ~200 LOC for WS route + per-session
  subscriber set, ~100 LOC of client wiring, ~100 LOC of tests).
- **Deps:** H1.1 (event log fan-out), H2.2 (ConversationState).
- **Pairs with:** the H0.6 web-UI smoke test (extension: assert the
  WS endpoint exists and broadcasts).
